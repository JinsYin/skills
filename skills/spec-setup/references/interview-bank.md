# 问题库（新项目版）

`spec-triage` 的访谈是**补问**——勘察定不了的才问。新项目没有代码可取证，访谈是**唯一输入**，量大得多。

规则不变：用 `AskUserQuestion` 批量提问，一轮不超过 4 个，**一次走完**（约 3-4 轮）后统一写入。写一半停下来问，会留下半套规范——比没有更难收拾。

## 第一轮：形态与模块

### 形态（多选）

> 这个项目包含哪些形态？可多选：Web fullstack / 后端服务（纯 API）/ Mini Program / Android App / iOS App / CLI 工具·SDK 库 / 桌面应用。

多选是常态。不要默认单形态然后事后补。

### 模块映射（多形态时必问）

> 每个形态落在哪个目录？目录还没建也说计划路径。

这是 `paths:` 的唯一输入。没有它就只能写全仓通配。

### 起点确认（勘察有歧义时）

> 仓里已经有 N 个源文件 / 已有 `CLAUDE.md`。这是新项目还是已经开工一阵了？

有实质业务代码就该走 `spec-triage`。宁可多问一句。

## 第二轮：栈的缺口

对矩阵里没覆盖的部分逐项确认。**每个推荐都先给理由再问**——没有理由的推荐会被随口接受，而随口接受的会被写成规范。

> 小程序端没有对口 best-practices。建议原生 + TypeScript 而非跨端框架：本项目只有一个小程序目标，跨端抽象层在单目标下只剩成本。接受吗？后续要上多端的话这条要重新裁决。

### 摇摆时的追问

> 后端在 Java 与 Go 之间没定？选 Java 的话 `spring-boot-best-practices` 的 40 条规则立刻到位；选 Go 则规范要从零建。有没有硬性理由指向 Go？

成本差是真的，要摆出来，但不要替用户决定。

### 版本

> 有没有指定版本或版本下限（团队环境、客户要求、依赖约束）？没有的话我走 Context7 取当前稳定版。

## 第三轮：边界与裁决

### 硬约束 vs 偏好

> 刚才定的这些，哪些是**违反即打回**，哪些只是"最好这样"？

全标硬约束等于没分级，冲突时 agent 无从取舍。

### 禁区与锁定决策

> 有没有已经拍板、不允许被"优化"掉的决策？有没有不能动的目录或文件？

新项目也有这类东西——通常来自上一个项目的教训、合规要求、或对接方的硬性约定。**不写进常驻层，会被自动审查反复当成缺陷"修复"。**

### 未来意图

> 半年内有没有已知的方向？（要拆服务、要上多端、要换数据库、要开源）

代码里一点痕迹都没有，只在人脑里。规范若与方向相反，会在转向时变成阻力。

## 第四轮：留白（本 skill 的分水岭）

**这一问必须主动问，用户不会自己提。**

> 命名细则、错误码编排、测试分层、日志规范这几块，现在拍板还是等首个模块落地后再定？现在定的话我需要你给出具体规则；不定的话我记进留白清单，等触发点到了再回来补。

### 为什么要主动给"不定"这个选项

不给，用户会默认"既然在建规范，那就都定了吧"，然后随口给出没想清楚的答案——那正是猜写的来源。**给出「现在不定」这个正当选项，是本 skill 与模板方案的核心差别。**

### 触发点

> 什么事件发生后回来复查？默认是：首个模块合并后、首次代码审查后、引入第二个形态时。

默认值可以直接采纳，但要让用户看见——它会被写进 `CLAUDE.md` 常驻层。

### 拿不准归属时

> 这条约定换个项目还成立吗？

用户也答不上来就放项目层。**放窄了容易改，放宽了会污染其他项目。**

## 不要问的

- 锁文件、构建文件里能查到的（脚手架已生成时，栈直接取证，只补问未定项）
- 有明确社区默认的（除非用户主动要偏离）
- 细到实现层的（"日志用哪个 appender"——这属于首个模块落地时的决定，不是建规范时的）
- 一次超过 4 个——超出后回答质量明显下降
- **任何你打算写进规范却没人拍过板的** —— 不是"不要问"，是不问就不许写（`guards.md` G11）
