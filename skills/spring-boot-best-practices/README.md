# spring-boot-best-practices

Coding conventions and architecture rules for Spring Boot 3 + Java 21 + MyBatis-Plus backends: 49 rules across 8 categories.

Structure modeled after [vercel-labs/agent-skills](https://github.com/vercel-labs/agent-skills/tree/main/skills/react-best-practices).

## Why this layout

Two ways to feed conventions to an agent:

| | Path injection (`.claude/rules` + `paths:`) | Progressive disclosure (this layout) |
|---|---|---|
| Loading | Auto-injects full file on glob match | Agent reads index, opens individual rules on demand |
| Granularity | One large file per topic | One small file per rule |
| Failure mode | Wrong glob → never matches, or matches everything | Weak index → misses the right rule |
| Addressability | No slug; cannot cite a single rule | Stable slug per rule; reviews can cite by name |

Path globs fail silently: in our earlier ruleset, 11 files included planning-artifact globs in `paths:`, injecting ~10.5 KB into every planning step, while a React rule pointed at `**/*.vue` in a repo with zero `.vue` files and never fired once. Progressive disclosure avoids path-glob machinery altogether.

## Layout

```
SKILL.md            Index: 49 slugs + one-line summaries + task routing table (~5 KB)
rules/
  _sections.md      Category definitions: ID / order / impact / description (build input)
  _template.md      Single-rule skeleton
  <prefix>-<slug>.md  Rule body, ~800 B average
AGENTS.md           Full compiled bundle (~50 KB), generated by scripts/build.sh
scripts/build.sh    _sections.md + rules/*.md → AGENTS.md
metadata.json       Version, abstract, references
```

## Impact levels

Graded by **consequence of violation**, not frequency — this decides which rule wins on conflict:

| Level | Meaning | Categories |
|---|---|---|
| CRITICAL | Immediate bug, security vulnerability, or startup/runtime failure | `layer-` `crypto-` `entity-` |
| HIGH | Runs, but fails review and forces rework | `db-` `envelope-` `dto-` |
| MEDIUM | Inconsistent, though functionally valid | `naming-` |
| LOW | Style preference | `stack-` |

## Adding a rule

1. Copy `rules/_template.md` to `rules/<prefix>-<slug>.md`, using a prefix from `_sections.md`.
2. Write the body — **must** explain *why* and the *consequence of violation*; bare imperatives without rationale get low compliance.
3. Add one index line under the matching category in `SKILL.md` with clear trigger cues.
4. Rebuild `AGENTS.md`: `bash scripts/build.sh`.
5. Verify 1-to-1 parity between index and rule files:

```bash
index_file="$(mktemp)"
rules_file="$(mktemp)"
trap 'rm -f "$index_file" "$rules_file"' EXIT
grep -oE '^- `[a-z]+-[a-z-]+`' SKILL.md | tr -d '`' | sed 's/^- //' | sort > "$index_file"
ls rules/[a-z]*.md | xargs -n1 basename | sed 's/\.md$//' | sort > "$rules_file"
diff "$index_file" "$rules_file" && echo OK
```

Index/file drift is the only silent failure of this layout: an extra index entry breaks `Read`; a missing index entry hides the rule forever. Run the check after every change.

## Enabling

Place the skill where Claude Code discovers it:

```bash
# Global (all projects), from repository root
mkdir -p "$HOME/.claude/skills"
ln -s "$(pwd)/skills/spring-boot-best-practices" \
      "$HOME/.claude/skills/spring-boot-best-practices"

# Or per project
mkdir -p "<project>/.claude/skills"
ln -s "$(pwd)/skills/spring-boot-best-practices" \
      "<project>/.claude/skills/spring-boot-best-practices"
```

Symlink rather than copy — this repository stays the single source of truth.

## Boundaries

This skill is a **cross-project** baseline. Package names, module splits, migration location layers, and locked domain decisions belong to each project's `CLAUDE.md`, which wins on conflict.

Do not copy rule bodies into a project's `CLAUDE.md` — `CLAUDE.md` loads in every session, multiplying token cost across sessions while the two copies inevitably drift apart.
