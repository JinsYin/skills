# 设计工具方言

`export --tool <name>` 的裁剪规则。

同一份 `CURRENT.md` 直接丢给不同工具，效果差别很大——不是因为工具能力差异，而是**吃的输入形状不同**：v0 要单组件粒度且要点名 shadcn primitive，Figma Make 给一张参考图比给两千字管用，Lovable 要完整产品 brief 含数据实体。

## 通用规则

无论哪个工具，产出的 prompt 包都以一段**上下文块**开头，再接请求。这段抄 `CURRENT.md` 的「给 AI 设计工具的上下文」章，按目标工具删减。

三条通用裁剪：

1. **删掉溯源行**（`> 来源：V1 → V2…`）——对设计工具是噪音
2. **保留「明确不做」**，且提到最前面（放末尾会被长上下文稀释）
3. **保留「前置条件」列**——按钮什么时候灰、什么时候不显示，是设计工具最常画错的地方

## v0（Vercel）

**吃**：单个组件或单个页面的精确描述，点名 shadcn/ui primitive。
**不吃**：整站规范、多页面、导航结构。

裁剪：

- 每次导出**一个页面**，文件名 `v0-<页面id>.md`。要多个页面就跑多次
- 上下文块压到 5 行内
- 把「布局骨架」翻译成 shadcn primitive 名：筛选区 → `Card` + `Input` + `Select` + `Button`；主表格 → `Table`；右侧详情 → `Sheet`；确认弹层 → `AlertDialog`；表单 → `Form` + `react-hook-form`
- 「数据与字段」表原样保留，示例值很重要——v0 会拿它生成 mock 数据
- 「操作」表保留，二次确认那列直接映射成 `AlertDialog`
- 全局约定只带**与本页相关**的那几条

结尾固定加一句：`只用 shadcn/ui 组件与 Tailwind 工具类，不要引入其他 UI 库；不要自造色值，用 CSS 变量。`

## Figma Make

**吃**：参考图 + 精简 brief。
**不吃**：超长文字规范。

裁剪：

- 上下文块保留，产品定位那两句要写好——Figma Make 靠它定调性
- 页面规格**只保留**「目标」「布局骨架」「数据与字段」三节，操作与状态压成一段要点
- 产出末尾提示用户：**同时附上 `.product/design/` 里对应页面的截图**，效果比纯文字好一个数量级。若 `.product/design/screenshots/` 有对应文件，把路径列出来
- 「明确不做」保留，但改写成祈使句（`列表用表格，不要卡片`）

## Claude Design / Claude Artifacts

**吃**：完整结构化规范，长上下文无压力。

裁剪：

- **整份 `CURRENT.md` 直接给**，只删溯源行
- 若项目有 `tokens.css` / `design.md`，一并附上，并说明视觉值一律取自它
- 可以一次要多个页面，但明确要求「先出信息架构与一个页面，确认后再铺开」

## Lovable

**吃**：完整产品 brief，含数据实体与鉴权。
**不吃**：只给一个页面（它会自己脑补出整个应用）。

裁剪：

- 保留全部七章
- **额外补一节「数据实体」**：从各页面的「数据与字段」表反向归纳出实体及其关系（如 机构 1—n 应用，应用 n—n 场景）。Lovable 会据此生成数据层，不给它就自己编
- 补一节「鉴权与角色」：直接用 baseline 的角色权限矩阵
- 明确说明**不要**生成后端（若项目后端已存在）

## 产出位置

写到 `.product/spec/<产品线>/.export/<tool>-<页面id|all>.md`。

`.export/` 是临时产物，建议加进 `.gitignore`——它随时能从 `CURRENT.md` 重新生成，入库只会制造第三份会漂移的副本。
