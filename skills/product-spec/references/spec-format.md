# 规范格式定义

本文件是格式的权威定义。骨架见 `templates.md`，合成算法见 `synthesis.md`。

## 目录与命名

```
.product/spec/
├── README.md
├── <产品线>/
│   ├── CURRENT.md            # generated，只由 sync 写
│   ├── V1__baseline.md       # 全量基线，每条产品线有且仅有一个
│   ├── V2__<slug>.md         # 增量变更
│   └── V3__<slug>.md
└── <另一条产品线>/
```

- **产品线目录名**用小写 ASCII，与前端路由或原型目录对齐（`console`、`portal`、`connector`）
- **版本号**每条产品线**独立编号**，从 1 连续递增，不跳号不重号
- **slug** 小写 + 下划线，只用 ASCII，概括这次变更（`data_space`、`audit_center`）
- 文件名的 `V{n}__` 必须与 frontmatter `version` 一致

命名仿 Flyway 是为了「按序重放」这层语义，不是为了跟数据库迁移共用工具——两者没有任何耦合。

## frontmatter

### V 文件

```yaml
---
product: console            # 产品线，与所在目录名一致
version: 2                  # 整数，与文件名 V2__ 一致
slug: data_space
title: 数据空间架构重构      # 中文，一句话概括
type: change                # baseline | change；V1 恒为 baseline
status: active              # draft | active | superseded
created: 2026-08-05         # 绝对日期，不写「上周」
---
```

`status` 语义：

| 值 | 含义 | 能否修改文件 |
|---|---|---|
| `draft` | 起草中，尚未定稿 | 能，随便改 |
| `active` | 已定稿，构成当前态 | **不能**。要改就发新 V |
| `superseded` | 整个 V 被后续版本整体推翻（罕见） | 不能。且 `sync` 跳过它 |

### CURRENT.md

```yaml
---
product: console
synthesized_from: [1, 2, 3]      # 参与合成的版本号，升序
generated: 2026-08-05
generator: product-spec skill
includes_draft: false            # 若纳入了 draft 版本则为 true
---
```

正文第一行必须是：

```
<!-- GENERATED by product-spec sync — 勿手改。要改内容请新增 V 文件后重新 sync。 -->
```

## 定位符（locator）

变更清单靠定位符锚定目标，它同时是合成算法的输入。全小写点分路径，段内可用中文：

| 形式 | 指向 |
|---|---|
| `nav.<分组>` | 导航分组 |
| `nav.<分组>.<页面id>` | 导航项 |
| `page.<页面id>` | 一个页面 |
| `page.<页面id>.layout` | 该页面的布局骨架小节 |
| `page.<页面id>.fields.<字段名>` | 页面内某个字段/表格列 |
| `page.<页面id>.actions.<操作名>` | 页面内某个操作 |
| `page.<页面id>.states` | 该页面的状态与流转小节 |
| `flow.<流程名>` | 一条跨页面流程 |
| `term.<术语>` | 术语表条目 |
| `global.<约定名>` | 全局约定章节里的一条 |
| `donts.<条目>` | 「明确不做」里的一条 |

**页面 id 必须与原型/前端代码里的 id 一致**（如 `apps`、`complianceStats`），别自创。这是规范和实现之间唯一的硬锚点，断了之后 `check` 就查不出漂移。

## 变更操作

| 操作 | 语义 | 定位符要求 | 必须补充 |
|---|---|---|---|
| `ADD` | 新增 | 目标**不得**已存在 | 新增页面写全量六小节；新增字段/操作补该行 |
| `MODIFY` | 就地改内容 | 目标必须存在 | 改后的完整内容（替换而非追加） |
| `RENAME` | 改名，语义不变 | 目标必须存在 | 新名字。旧名进术语表的「历史别名」 |
| `MOVE` | 位置变了，内容不变 | 目标必须存在 | 新位置的定位符 |
| `REMOVE` | 删除 | 目标必须存在 | 删除理由（一句话，追溯要用） |

`RENAME` + 内容也改 = 拆成 `RENAME` 一行 + `MODIFY` 一行，别糊在一起，合成时会歧义。

## V1__baseline.md 章节（固定顺序）

1. **产品定位与角色** — 谁在用、解决什么问题、角色权限矩阵（表：角色 × 模块 → 可见/可写）
2. **信息架构** — 导航树，分组 → 菜单 → 页面 id，含层级与折叠关系
3. **全局约定** — 布局骨架、列表页/详情页/表单的通用模式、状态与反馈通则、权限可见性规则。写这里的东西不要在每个页面里重复
4. **页面规格** — 每个页面一节，六个固定小节，见下
5. **关键流程** — 跨页面端到端流程，编号步骤；分支多时配 mermaid
6. **术语表** — 中英对照 + 定义，锁定对外文案与枚举中文名
7. **明确不做（Don'ts）** — 见下，**别省这章**

## 页面规格的六个小节

每个页面重复这六节，顺序固定，缺一节就写「无」而不是删掉——设计工具靠结构稳定来对齐。

| 小节 | 写什么 | 不写什么 |
|---|---|---|
| **标识** | 页面 id、路由、入口来源（从哪个菜单/按钮进来） | — |
| **目标** | 一句话：用户来这个页面干什么 | 长篇背景 |
| **布局骨架** | 文字线框，区域级：顶部筛选区 / 中部表格 / 右侧抽屉 | 像素、色值、字号、间距 |
| **数据与字段** | 表：字段 / 类型 / 示例值 / 是否可编辑 / 说明。示例值要真实感 | 数据库列名、接口字段名 |
| **操作** | 表：操作 / 触发位置 / 前置条件 / 结果 / 是否二次确认 | 后端实现 |
| **状态与流转** | 空态、加载态、无权限、错误、极值（超长文本/大数字/零条）；跳转去哪、从哪来 | — |

**「前置条件」这列最容易被略过，但它是设计工具画不对的主因**——按钮什么时候是灰的、什么时候根本不显示，不写它就只能靠猜。

## Vn 变更文件章节（固定顺序）

1. **变更摘要** — 一句话 + 动机（**为什么**改，不是改了什么）
2. **变更清单** — 机器可读锚点，`sync` 只认这张表

   | 操作 | 定位符 | 说明 |
   |---|---|---|
   | `RENAME` | `page.orgs.fields.关联应用` | 改叫「关联空间」，展示机构加入的数据空间列表 |

3. **新增页面规格** — 与 baseline 相同的六小节，全量写
4. **修改的页面** — 只写 delta，每条必须点名替换哪一小节
5. **流程与术语变更**
6. **影响面** — 被间接波及但本次不改的既有页面（给设计和测试看的）

## 「明确不做」为什么必须写

借鉴 [design.md](https://designproject.io/blog/design-md-file/) 的经验：约束比描述更能定形。AI 设计工具的失败模式不是「画不出来」，而是「自作主张多画了」——给列表加个它以为你想要的批量导出，给表单加个记住我，给详情页加个 AI 摘要卡片。

这章就写这些：

- 本产品**不做**的功能（及一句话理由）
- 界面上**不要出现**的元素（如：不要面包屑、不要卡片式列表、不要空状态插画）
- 已经评估过并否决的方案（防止下次又被提出来）

一条一句话，越具体越好。「不要过度设计」是废话，「列表页不要用卡片布局，一律用表格」才有用。
